# PT-002: OTP rate limiting and brute-force protection

**At most 5 OTPs to one email in 1 hour.**

- `OTP_SEND_MAX_PER_IDENTIFIER = 5` sends per email.
- `OTP_SEND_WINDOW_SECONDS = 3600` (1 hour) window.
- One IP address can send at most **20** OTPs in the same 1-hour window
  (`OTP_SEND_MAX_PER_IP = 20`), across all emails.

The 6th send to the same email in the window gets
`429 OTP_RATE_LIMITED` with a `Retry-After` header.

### Wait between two sends (resend cooldown)

Each send makes the next wait longer (exponential backoff, multiplier 2,
maximum 15 minutes):

| Send | Wait before the next send |
| --- | --- |
| 1st | 60 s |
| 2nd | 120 s |
| 3rd | 240 s |
| 4th | 480 s |
| 5th | 900 s (cap) |

So the 5 sends take at least about 15 minutes (0 s, 60 s, 180 s, 420 s, 900 s).
If the send fails because of a server error, the cooldown is given back so the
user can try again at once. The counters stay.

## Verify protection (wrong codes)

| Rule | Default |
| --- | --- |
| Lifetime of one OTP | 600 s (10 min) |
| Wrong codes on one OTP before it is deleted ("killed") | 5 |
| Verify calls from one IP per window | 30 per 15 min |
| Wrong codes per email with no wait | 3 |
| Wait after more wrong codes | 5 s, 10 s, 20 s, … up to 300 s |
| Killed codes per email before a lockout starts | 1 (the 2nd killed code locks) |
| Lockout lengths | 15 min, 1 h, 4 h, 16 h, then 24 h max |
| Lockout level reset | 24 h with no new lockout |

A correct code clears the wrong-code count, the wait and the lockout level
for that email. An expired code is logged but not counted as a wrong code.

### Requests without an email (old app builds)

`OTP_VERIFY_REQUIRE_EMAIL = false` for now. Until the new mobile release sends
`email` on verify-otp, requests without an email are limited per IP: 10 wrong
codes from one IP in 15 minutes locks that IP. The limit is high because
schools and campuses share one public IP.

## Error responses

| Status | Code | When |
| --- | --- | --- |
| 429 | `OTP_RATE_LIMITED` | Too many sends/verifies, or inside a cooldown/wait |
| 429 | `OTP_LOCKED` | The email (or IP, legacy path) is locked |
| 503 | `OTP_PROTECTION_UNAVAILABLE` | Redis is down on send |

The 429 body has `retryAfterSeconds`; the same value is in the `Retry-After`
header (exposed through CORS).

## Other points

- **Routes:** `login` (sends the OTP / magic link) and `verify-otp`.
- **Send fails closed:** if Redis is down, no OTP is sent (stops inbox flooding).
- **Verify fails open:** if Redis is down, sign-in still works. The per-code
  cap and single use are enforced in PostgreSQL, so the code still cannot be
  brute-forced.
- **No account discovery:** known and unknown emails are counted the same way.
  Emails are stored in Redis only as a hash (`OTP_HASH_SECRET`).
- **Database:** migration `0098_add_otp_attempt_tracking.sql` adds failed
  attempts and last send time to the OTP token.
- **Proxy:** set `TRUST_PROXY_HOPS` to the real number of proxies so per-IP
  limits see the real client IP. A higher value lets clients fake their IP.
- **Logs:** OTP codes are removed from request logs.
- **Config docs:** `api/.env.example` and
  `api/docs/aws-parameter-store-multi-environment-guide.md`.
  `OTP_LOCKOUT_STEPS_SECONDS` is no longer read; remove it where set.
